## Layering
- `Simulation`: math data only; pure-ish tick(state, input, track, parameters) -> new state/events. No game globals.
- `Track`: analytical/collision world, checkpoint gates, item/hazard spawn coordinates. Data-driven; explicit track version + checksum/hash for multiplayer and replays.
- `Race`: current pure fixed three-lap solo lifecycle (countdown/running/finished/stopped/interrupted) around Laps; other race modes remain future work.
- `Checkpoints`: pure local sequence progress over ordered directional Track gates.
- `Laps`: pure repeatable practice laps and integer tick timing around Checkpoints; no countdown, fixed race length or winner lifecycle.
- `PeerSession`: implemented pure two-peer invite/join/ready/start-proposal state, scoped identity/compatibility, paced control output and bounded retries/timeouts. Presentation consumes copied views; no live race or tick authority is supplied.
- `LiveRace`: pure bounded owner of one RaceStart bundle, actual fixed-step local race lifecycle and observational peer poses; no native/UI calls, trusted remote progress or shared winner.
- `LiveProtocol`: strict 40-byte version 2 pose codec on AZKRUN2, including state time since mapped GO; separate from control/clock/profile/probe prefixes. Both peers need the same version; no legacy fallback.
- `RaceGrid`: pure fixed cosmetic-profile agreement on AZKGRD1 and deterministic role-based grid slots; no native calls, frame owner, independent native sender, simulation clock or race authority.
- `GameSession`: future production game mode, participants, tick authority and reproducible event log; not an alias for PeerSession or the observational candidate.
- `Input`: front-end state sampling; clears stuck keys on focus loss/combat; keybind remapping requires API tests.
- `Renderer`: world-to-canvas transform; viewport/UI scale; textures from fixed pool; minimap optional.
- `Network`: transport rate budget, codec, protocol state machine, ACK/retry/recovery; not used by simulation tests.
- `Persistence`: schema v1 and migration; never serialize live per-frame state excessively.
- `Presentation`: pure local render-pose interpolation, uniform viewport/camera mapping, clipped rectangle projection, scalar HUD mapping and bounded cached observational peer forecasts. These values never feed simulation.
- `Circuit`, `CapitalCities`, `Courses` (integrated from `claude/capital-cup`): `Circuit.new` builds a pure street circuit (capsule road and walls, plazas, solid boxes) from generated `CapitalCities` data; `Courses` is the presentation-side catalog of cups and courses that `UI` and `Menu` read and that builds each course's pure track ([Stormwind sheet](art/tracks/stormwind.md), [contract](API_CONTRACTS.md#proposed-capital-cities-cup-city-circuits-and-the-course-catalog)). Physics uses a city circuit through the existing track interface.
- `Menu` (implemented and integrated on `codex/ui-backend-integration`): the front end's screens, navigation, race HUD, results dialog, settings and saved preferences, as client presentation over `UI`'s existing commands ([front-end sheet](art/ui/front-end.md)). It never writes run, race, physics, input or session state.
- `Diagnostics`: opt-in perf/FPS statistics, protocol rate metrics, error logs, feature gates.

## API interaction restrictions
Current WoW API calls live in `UI`, `Menu`, `Core`, the explicitly armed `TransportProbe` experiment and `SessionTransport` adapter. The experiment reuses IOU's client-tested logged WHISPER route (`SendAddonMessageLogged` / `CHAT_MSG_ADDON_LOGGED`) and complete Forever first-name/surname identities, with no realms or fallback; see [ADR 0012](adr/0012-forever-logged-transport.md). Pure modules, including `NetworkProbe`, `RaceProtocol`, `PeerSession`, `ClockProtocol`, `StartClock`, `RaceStart`, `RaceGrid`, `LiveProtocol` and `LiveRace`, do not call them. Production synchronization is still proposed; the standalone probe neither reads nor writes vehicle/race state. No math library calls UI setters. Do not call secure/protected APIs or rely on secret-value readback. No special treatment of combat information is needed.

## Simulation clock
- Fixed dt = 1/60s; `OnUpdate` adds elapsed; execute at most 5 catch-up iterations/frame, then bound accumulator and record dropped simulation time.
- The simulation input sample for each tick is derived from current key state, not collected as raw frames.
- Active rendering interpolates previous/current positions using `clock.accumulator / clock.dt` and shortest-arc heading. This introduces at most one fixed step of visual delay, including frames without a simulation step. Start/Create and Stop draw the exact current pose; inactive updates and reopening retain it. Do not mutate physics through UI animation.
- Stop on focus loss/reload. Combat ends the game, closes the window and records an interrupted result once (ADR 0006); no automatic resume. Race results will freeze actual current standings when that engine exists. Anti-cheat timestamps cannot rely solely on mutable system time.

## Two-peer grid, countdown and observational display

The current live flow is explicit Host/Listen with a fixed cosmetic kart, Join, bounded RaceGrid agreement, Ready, host PrepareStart, clock negotiation, staged `GET READY`/`3/2/1`, then mapped GO. RaceGrid's 12-byte PROFILE/ACK messages exchange known kart IDs for the configured peer/session only. Ready and PrepareStart require profile agreement. Fixed roles place the two kart centres 18 units either side of the original spawn, 36 apart, with matching facing and validated finite road positions; the track definition remains unchanged. The copied grid view supplies local/peer poses and kart IDs, not authoritative states. Ten cosmetic choices still mean exactly two supported participants.

SessionTransport remains the sole native output/lease owner through every phase. Control, AZKGRD1 profiles, AZKCLK1 coordination and AZKRUN2 telemetry share the persistent 500 ms spacing, 2 calls/rolling second and 158 payload-plus-prefix bytes/rolling second limits. The separate standalone probe cannot run concurrently. Profile agreement is bounded to 3 PROFILE attempts with 2 s retries, a 10 s deadline, 64 decoded events, 8 events/s and 8 deferred messages. Peer-profile contradiction, native refusal and lifecycle/focus failures close/cancel instead of selecting a guessed profile. Message callbacks do not send, create frames or take over the update lease.

Live coordination opts into `countdownMS=3000`; backend-only legacy coordination defaults0. Clock negotiation must finish before the final three seconds. UI stages both selected sprites while waiting and retains held throttle, but performs no Physics, lap or checkpoint steps before GO. The actual backend bundle adopts the role's grid spawn at tick zero exactly once, without replaying the solo countdown. UI consumes copied cue/epoch views and must not take the one-shot ticket. Leaving/failing on the grid releases capture without inventing a race result. Offset uncertainty and final-ACK/CANCEL loss can still produce asymmetric arming/start; this design makes no atomic-start guarantee.

AZKRUN2 is a breaking experimental telemetry revision: exact 40-byte packets include `sampleMS`, the latest advanced sender-state time since its own mapped GO. There is no old-wire fallback. Copied LiveRace views expose elapsed time and `remote.sampleAgeMS=max(0,receiverElapsedMS-remote.sampleMS)` while retaining receive age/staleness. This estimates observation age including transit; clock-offset uncertainty prevents treating it as measured one-way latency. Existing sequence/tick/peer/session/progress bounds remain and sample stamps cannot regress. Positions/progress are observational and never correct the local kart or award checkpoints.

UI uses the existing opponent Texture for the agreed sheet/image and heading/pivot, with a guarded primitive fallback; files are loaded once per profile change rather than each render. The local follow camera is unchanged. Off-screen peer direction/distance text explains missing markers; these estimates do not establish who is ahead. Presentation builds at most 31 cached 60 Hz points once per observation and samples them using state age, removing the previous extra snapshot-interval buffer. Its 500 ms forecast caps absolute speed 260 units/s and yaw 2.6 radians/s, uses measured travel direction where valid and stops on geometry contact/clamp. Road-only fallback rejects outside endpoints; existing geometry guarantees still apply. Non-running or malformed observations freeze or hide safely. Sampling allocates no pose tables and never steps local simulation. Unknown braking/steering, stale data and clock error can cause corrections at the next packet; this is bounded display estimation, not verified remote physics.

The explicit UI pool remains 79 frames/166 textures/81 font strings, not a native memory/FPS measurement. Current forecasts, peer-art loading, grid input/cleanup, full countdown visibility and two-client feel require actual-client verification (**NOT RUN for this revision**). Contact physics and agreed results remain absent; local finishes continue to be labelled unverified. These constraints preserve the measured gate instead of claiming that code or mocked peers establish production multiplayer.

Checkpoint/lap progress is independent of physics compatibility version8. After each actual fixed physics step, UI passes previous/current simulation coordinates and the new tick to pure Race, which delegates through Laps to Checkpoints. Immutable checkpoint progress stores `nextGate`, `passed`, `complete` and `lastTick`; only the expected gate can award, at most once per consecutive bounded step. Strict directional finite-segment crossing avoids awards when departing from the gate line or crossing backwards. Duplicate, stale, out-of-order or gapped tick reports return the same progress unchanged, with no automatic gap recovery. Only consecutive samples with nonfinite positions or movement over five units consume their tick without an award, allowing a following valid consecutive step to recover. This is local consistency, not a security guarantee or competitive route validation.

Laps stores `checkpoints`, `completedLaps`, `lapStartTick`, `currentLapTicks`, `lastLapTicks`, `bestLapTicks`, `bestLapNumber`, `lastTick` and `lastFinishTick`. In the UI run, the first lap begins at GO, including acceleration after release from the grid. Each fourth award completes exactly one lap, records its integer tick duration and rearms North at the same finish tick; the next lap starts at zero with no counted tick lost. Consecutive invalid movements advance time but not gates; rejected duplicate/older/gapped reports change neither. `bestLapTicks` and `bestLapNumber` begin nil and change only on a completed lap with a strictly smaller integer duration; ties keep the earliest lap, and incomplete laps never compete. New Laps state, including the GO reset, clears this in-memory best. Standalone Laps remains repeatable without a fixed limit. Display multiplies tick counts by the fixed step; elapsed seconds exclude dropped simulation time and stopped periods.

Race injects Checkpoints and Laps explicitly and stores status, lap progress, a three-lap target, countdown progress, start/last/finish ticks, total elapsed ticks and reason. The third accepted lap sets `finished` and its finish tick once. `Race.stop` records an actual partial stopped/interrupted result during countdown or running; every later step or stop returns the identical terminal object. The current-run best is retained in terminal/reopened results, including rejected Start attempts; only a successful fresh Start/Restart resets it. Race itself has no persistence or remote classification. The independent SoloRecords/Highscores boundary saves eligible solo totals across runs; ghosts remain deferred.

Physics stores normalized `steering` alongside the other fourteen state fields, including the v6 correction counter `driftGraceTicks`. It approaches a held turn at 8 units/s and centers at 16 units/s, resolving reversal through center before building the opposite sign; both raw turn directions force immediate zero. New drift entry requires the progressive steering sign to agree with exactly one raw turn direction. Existing held drift pauses charge through up to twelve correction ticks; matching steering resumes it in either direction, while the thirteenth invalid tick clears charge. Brake, low speed, rough ground and wall contact cancel immediately. Wall contact resets steering; grass retains it. This adds no UI setting, object, input-capture behavior or client API dependency. Exact tuning and pending direct-play validation are recorded in [PHYSICS.md](PHYSICS.md).

`Presentation.pose(previous, current, alpha)` returns scalar x, y and heading, interpolating through the shortest heading arc without mutating either state or allocating a pose table. UI retains the actual state immediately before each fixed step, then renders between that and the latest state after catch-up. Input sampling, collision, drift, boosts, surface feedback and timing use actual simulation state; no interpolated coordinate becomes simulation input. Stop redraws the exact current pose without changing the frozen clock remainder. The renderer uses existing pooled objects and does not add per-frame chat.

Space samples a held drift intent. Physics alone owns charge, correction grace, signed slip, boost ticks and current surface; drift yaw is 0.75 of ordinary yaw and charge tiers take 30/60 valid ticks. A valid Space release can spend a retained tier during correction grace.
