## F1: rendering and bounded timing

**M0 claim:** the pooled primitive oval and one kart render correctly without growing the addon's explicitly allocated UI object counts during repeated drives. This is a small workload, not the future 32-sprite benchmark.

**Historical short smoke, 2026-10-18:** the oval and orange kart rendered at 1920×1080, normal `uiScale=1`, `useUiScale=0`; Start advanced ticks. One stopped probe reported `frames=1871`, `ticks=534`, `maxElapsed=0.0310`, zero dropped time/hitch frames and UI counts of 6 frames/99 textures/3 font strings. A closed-window whole-client FPS sample was `207.6124420166`. These were short observations, not rotation/handling proof, addon CPU cost or scaling/stress acceptance. A single W tap did not give clearly measurable displacement at that time; the later human drives below supply movement/rotation evidence. No AzerothKart error dialog was visible, but error/taint logging was not enabled.

1. Out of combat, open `/akart`, run `/akart probe`, and record FPS using `/dump GetFramerate()` before starting. Capture resolution, UI scale and a screenshot of the window.
2. Click **Start Test Drive**, verify the HUD resets to tick 0, then drive and steer manually for approximately 60 seconds using an independent timer. Press Escape, dismiss the normal game menu if opened, then run `/akart probe`. Do not type the command during an active timing sample: opening chat deliberately ends capture.
3. Record external duration, reported `activeFrameSeconds`, `simulatedSeconds`, `callbackHz`, `frames`, `ticks`, `maxElapsed`, `droppedSeconds`, `hitchFrames`, accumulator, stop reason and addon frame/texture/font-string counts. The stopped HUD tick must match the probe tick immediately. Repeat the probe several seconds later without Start: timing values and ticks must stay frozen. Close/reopen must retain that stopped sample; only a deliberate new Start resets it. Repeat three drives. Counts must remain stable.
4. Repeat at UI scales 0.75, 1.0 and 1.25 **only if supported by the normal client UI**; otherwise record actual available scales. Do not force a hidden/unsupported CVar value. Check kart rotation, clipping, text and controls.
5. After the short F2 safety smoke passes, run 15 minutes idle/open and 10 minutes driving. Record before/after FPS, probe output, errors and visible hitches. Use the normal game FPS display if desired.

`activeFrameSeconds` sums valid `OnUpdate` elapsed values accepted during the active drive; it is not an independent wall-clock timer or CPU measurement. `simulatedSeconds` is `ticks × 1/60`; `callbackHz` is `frames / activeFrameSeconds` (zero before any elapsed time) and describes delivered callback cadence, not separately sampled whole-client FPS. Check `activeFrameSeconds ≈ simulatedSeconds + droppedSeconds + accumulator` at printed precision. Stop preserves the fractional accumulator for this accounting; it cannot advance while inactive, and Start creates a fresh clock.

`maxElapsed` is a whole-frame interval delivered to `OnUpdate`, not this addon's CPU cost. Dropped time measures bounded catch-up, not network loss or a pause duration. No chat output or UI object creation should occur every simulation tick. Reported object counts cover the UI module's explicit allocations; the bootstrap event frame, template internals and other addons require separate accounting. A long Alt-Tab interval may cause dropped time; there must be no long catch-up burst or automatic resume. The zeroed timing baseline and two stopped samples below are observed; the complete three-drive protocol and remaining F1 checks stay **PENDING**.

**Gate:** stable counts for this workload, readable primitives, no Lua/taint errors or visible sustained hitching attributable to the prototype, and F2 release tests passed. The future workload target (about 50 static sections, up to 32 moving sprites, at least 45 FPS on a recorded machine) remains untested. A claimed >10 ms addon overhead requires separate CPU profiling; frame intervals cannot establish that claim.

## F2: deliberate input capture and combat safety

The prototype starts only after **Start Test Drive** outside combat. Every subsequent mouse click releases capture, including clicks inside the canvas or an overlapping UI; this avoids guessing which non-text frame owns focus. Live Start/global-mouse ordering allowed capture; clicking Stop released through global mouse-down on this build. A stop clears held key aliases and freezes the clock, preserving its fractional accumulator for timing readback. Only a fresh Start discards that sample and resets the clock. Returning focus, ending combat, showing the window or logging in must never restart driving automatically.

**Partial live observation:** idle Escape released capture and opened the normal game menu; Close/reopen stayed stopped with ticks unchanged across the closed interval; first Enter released capture and opened chat; Stop released; idle Alt-Tab returned stopped through the unknown/Alt-key route. The owner subsequently reported actual combat closed the window, displayed the interruption note and left WoW controls working. Held throttle/release outcomes remain pending; simultaneous W/Up was explicitly skipped by the owner. [The evidence](evidence/2026-10-18-m0-client.md) separates observations, human reports and pending cases.

**Confirmed combat rule:** [ADR 0006](adr/0006-combat-interrupted-results.md) requires closing the racing window, stopping input/simulation and retaining **"Game interrupted by combat"**, with no automatic resume. Future race standings are finalized once from actual current placements. M0 has no standings and must not invent them. Close/note/terminal-once behavior is covered offline; the owner confirmed actual combat closure/message/working controls. Repeated events, retained note after deliberate reopen, no auto-resume and full taint auditing remain separate live checks.

Use [the client checklist](../tests/MANUAL_CLIENT_CHECKLIST.md) for sequential driving aliases, Escape, Stop, Close, chat/Enter and an unrecognized key, click outside, click chat or another UI, Alt-Tab, window hide/show, world transition, `/reload`, logout/login, opening/starting while in combat, and combat beginning during capture. Keep the owner's simultaneous W/Up row SKIPPED; do not request that combination again. After each performed stop check, verify ordinary WoW movement and chat manually. A status message alone does not prove keyboard consumption ended.

The probe reports optional game-window focus API availability and unavailable events. Required text-focus, combat, keyboard/propagation and global mouse-event support must be available for capture to start; missing required support fails closed. The two observed application-focus APIs are absent; idle Alt-key release does not establish the held-key/release-outside Alt-Tab case. Do not substitute the unrelated unit-focus event. Never invoke the restricted propagation setter during combat. Deferred restoration after combat is an implementation detail that must be tested against actual behavior and taint output.

**Gate — still pending:** every release route restores ordinary controls, Start is rejected in real combat, and combat interruption closes the window, stops simulation/input and retains one interruption note with no auto-resume or protected-action errors. Any stuck input or combat taint blocks M0; do not bypass it with protected-action tricks. A permitted on-screen-control fallback would require a separate scoped implementation and evidence.

Use two actual clients first, event sender identity, a fresh session ID and `AZKART1`. Test private `WHISPER` and `PARTY` separately, payloads of exactly 16/64/128/220 total message bytes, and 0.5/1/2/4 data packets per second for 120 seconds per window. ACKs and every participant's sends count toward the budget. Advance rates only while the prior window is stable. Record enqueue results separately from matched receipts, duplicates, reorder, timeouts, same-clock RTT and arrival gaps. Missing ACKs cannot alone distinguish data loss, ACK loss, delay, throttle or peer interruption.

Repeat direction A→B and B→A, then bidirectional traffic. Record city and instance conditions independently. Test reload/disconnect/reconnect with a new session; stale session packets must not count as valid receipts. Only add four/eight clients after two-client measurements and available consenting testers. Never send on each render or simulation tick and never use public chat for the probe.

**Gate:** measured sustainable aggregate traffic with reproducible recovery, followed by a recorded ADR selecting live-race research or asynchronous ghost/time-trial exchange. A transport pass is not a playable multiplayer pass. The later two-player race trial target remains an average handling/correction score >4/5 across five runs, no repeated teleport/collision/finish disagreement, and <1% ACK timeout in steady state under the chosen deadline. ACK timeout is an observable failure rate, not proven message loss. These are product targets pending evidence, not API guarantees.
