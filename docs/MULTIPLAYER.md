# Multiplayer experience & uncertainty

**Current priority:** genuine multiplayer precedes dedicated ghosts/time trials under [ADR 0010](adr/0010-multiplayer-release-priority.md). Release targets Codex's required work through verified multiplayer plus Claude's three ready maps/eight ready karts; roster size does not promise eight simultaneous racers. The first lowest-rate capability sample is complete; recovery, replication and scale acceptance remain open.

**Current implementation:** an explicitly armed, bounded two-peer **WHISPER_LOGGED** probe, using `C_ChatInfo.SendAddonMessageLogged` and `CHAT_MSG_ADDON_LOGGED` with native channel `WHISPER`, strict codec/accounting, one ACK per unique DATA, no retry/catch-up burst and explicit report/sequence evidence commands. The CSV channel label is `WHISPER_LOGGED`; no ordinary-whisper or unlogged fallback is provided. This is an experiment harness, not a lobby or live kart replication. [AKT722](evidence/2026-10-21-akt722-network-window.md) completed the 0.5 DATA/s, 16-byte, 120-second window on both peers: 59 accepted DATA → 59 unique receipts → 59 accepted ACKs → 59 matched ACKs, with zero observed rejections, duplicates, reorder, timeouts, late ACKs, outstanding ACKs, throttles or errors. Raw prefix/send results were numeric `0` on both sides. One terminal scheduled opportunity was not attempted locally, not lost in transit. Listener bitmaps show sequences 1–59 and an absent 60; owner bitmap portions are obscured, so preserve the count-reconciliation limit. Exact builds/interfaces, location and UTC test time were not supplied. Reconnect remains **NOT RUN**. See [ADR 0012](adr/0012-forever-logged-transport.md), [wire format and bounds](PROTOCOL.md), [source-backed API expectations](CLIENT_API.md#transport-probe-api-contract-source-evidence-not-a-live-pass), [experiment ledger](experiments/network-ledger.csv) and [two-client checklist](../tests/MANUAL_NETWORK_CHECKLIST.md).

**Measured latency, not a racing approval:** 59 RTT samples gave p50 697 ms, p95 779 ms, p99/max 881 ms. Listener gaps (58 samples) gave p50 1995 ms, p95 2094 ms, p99/max 2124 ms. Sender/listener elapsed totals were 130/147.325 seconds; these include different initial waits and cannot establish one-way delay. No numeric RTT acceptance threshold currently exists. Responsiveness, correction quality and start/finish agreement still need a real two-person candidate and direct play.

**Existing Forever evidence:** the sibling IOU repository records four exact logged-whisper round trips between two clients on 16 October 2026, build 70425, including ASCII, Norwegian UTF-8 and 239/240-byte packets (`IOU-GitHub/docs/connection-test.md`; identity/transport implementation in `IOU-GitHub/transport.lua`). We reuse that basic compatibility evidence. Forever character identities are full first names and surnames, without realms. Azeroth Kart accepts at most 96 raw name bytes before trimming/collapsing ASCII spaces; matching folds only ASCII case and preserves exact non-ASCII spelling, punctuation and hyphens across the complete native sender name. It never substitutes just a first name or invents a realm suffix.

## Realistic risk model
A smooth eight-racer kart game is a high-frequency interactive simulation. WoW addon messaging is a throttled control/message bus, not a dedicated UDP game-state networking API. A host with eight players can easily exceed aggregate message budget if naïvely sending one message per racer per render frame. Never build multiplayer architecture from imaginary 60Hz packet service.

## Implementation path
1. **Network transport gate:** AKT722 supplies the first lowest-rate sample. Next run one reverse-direction window on the same corrected build: owner listens, friend starts, fresh `AKT723`, **2 DATA/s, 128 bytes, 120 seconds** (NOT RUN). Nominal aggregate load is four DATA+ACK calls/s and 316 payload-plus-prefix bytes/s before overhead. Reconcile both reports/maps; preserve every timeout/error/throttle/disruption guard. This tests a combined direction/rate/size scenario, not an isolated comparison. Defer the exhaustive size/rate and PARTY/4/8 matrices; they are expansion work, not mandatory before preparing a bounded two-person candidate. Measure reconnect and the candidate's actual budget before a production architecture ADR; select replication from evidence. Logged payloads may be recorded or exposed by the client/server. The current harness does not implement the full gate.
2. **Low-rate social features**: presence, invites, rooms, track choice, ready checks, countdown and results, using the measured budget and tested `WHISPER`/`PARTY` behavior.
3. **Experimental 2-player race** with predicted local car, remote interpolation, host adjudication and debug overlay. Cap traffic, log corrections and finish disagreements.
4. 4-player beta only after repeated usable two-player sessions, 8-player beta only after measured successful 4-player tests.
5. **Deferred contingency**: bounded asynchronous ghost challenges may be discussed if live racing fails its gate; they are not scheduled ahead of multiplayer and do not silently satisfy the agreed release target.

## Proposed lobby UX
Private room invite (one-time, no scan/spam), host selection, player list, client compatibility warning, track/seed voting, synchronized race start; explicit Leave, Kick, Reconnect, Rematch. No public channel flood; respect user blocks/ignore where observable.

## Trust and result transparency
Host can edit their addon, so results are host-observed, not cryptographically provable; don't claim anti-cheat. Keep per-client diagnostic logs and "Unverified / Sync issue" on disagreement. A client must never be able to change another client's character or in-world motion.

## Eventual fallback decision
If synchronous play fails F4, stop and present measurements for owner review before changing the release scope. Ghost challenges/records/replays remain possible alternatives, not automatic substitutes. Revisit live racing on documented API/capacity improvement rather than repeated speculative rewrites.
